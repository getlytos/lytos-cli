# ISS-0097 — The agent never saw the CLI, and that is not its fault

## Field feedback (immo, 03–04/08 — the observation is Frédéric's)

An agent spent 48 hours of intensive Lytos use, having read ALL the rules at startup, and still
did every transition by hand (frontmatter edited, `git mv`, board regenerated) through throwaway
scripts — while `lyt start`, `show`, `close --dry-run` and `review --export/--accept` existed. The
cause: the generated rules mention only `lyt board` and `lyt close`, in passing, inside a table
cell. Nothing says "the CLI is the interface; never touch a frontmatter or a folder by hand".
Aggravating factor: `lyt` is not on the PATH (it is a devDependency) — the first attempt returned
"lyt not found", the agent concluded there was no tool, and the rules must therefore say `npx lyt`.

## The gesture

In the rule templates generated by `lyt init` (and in the method documentation):

- [x] A dedicated section, "The CLI is the interface": a table of verbs (start, move, close, show,
      review, board, lint) with when to use each — through `npx lyt`, never a bare `lyt`
- [x] The rule stated in the negative: "NEVER edit a status frontmatter or move a fiche by hand;
      when a transition has no verb, report it instead of working around it"
- [x] The session-start skill opens with `npx lyt show` (the real state in one call)
- [x] `lyt doctor` warns when a project carries rules from an earlier generation without the section

## Addition (validated on 04/08)

The generated rules section also carries the principle of **issue locality**: an issue lives in the
repository of the code that will close it, never in the one that discovered the need; a subject
touching two repositories becomes two cross-linked issues; and the overview is `npx lyt board`'s
job (multi-repo mode), not centralisation's. Template: the "Issues live where they will be closed"
subsection.

## Response to audit — 2026-08-10

**The [CRITICAL] finding is rejected, and it inverts the problem this issue exists to solve.**

`npx` resolves from `node_modules/.bin`, then `$PATH`, before ever touching the registry.
`package.json` declares `lyt`, `lytos` and `lytos-cli` as bins, so after the documented
`npm install -g lytos-cli` the name is on `$PATH`. Measured in a directory with neither
`node_modules` nor `package.json`: `npx lyt --version` → `1.4.0`, exit 0, no fetch.

The audit proposes replacing `npx lyt` with a bare invocation. That is exactly the failure
recorded in the field feedback above (line 28): in the immo project `lytos-cli` was a local
devDependency, a bare `lyt` returned `lyt not found`, and the agent concluded the tool did not
exist. `npx lyt` is the one form that resolves under **both** supported installs — global and
devDependency. Narrowing it would regress the incident that motivated the issue.

Checked residual risk: with `lytos-cli` installed nowhere, `npx lyt` falls through to the
registry, where `lyt` and `lytos` are both unregistered (404). Clean failure, no wrong package.

**Verdict contested → back to `4-review` for re-audit.** The generated rules stand as written.
